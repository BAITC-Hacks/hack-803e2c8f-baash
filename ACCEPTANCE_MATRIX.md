# Матрица приёмки Pulse 109

Это **критерии проверки**, а не утверждение, что каждый этап принят или что система готова к production. Фактическое состояние — в [матрице функций](docs/FEATURE_STATUS.md), разрывы с ТЗ — в [аудите](docs/review/COMPETITION_AUDIT_2026-09-29.md).

## Контрольные этапы

| Этап                         | Что должно работать                                                                                    | Чем подтверждать                                                          | Чего не заявлять                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| M0 · Основа репозитория      | Сборка сервисов, локальный запуск, единые команды.                                                     | Lock-файлы, CI, health checks, архитектурный тест.                        | Готовность к production.                                          |
| M1 · Контракты и данные      | Каноническая валидация, происхождение, карантин, качество времени, идемпотентный импорт.               | Контрактные тесты, миграции, обезличенные примеры, отчёт качества данных. | Охват отсутствующих регионов.                                     |
| M2 · Ручной критический путь | Приём, карточка оператора, решение, история статусов, аудит и outbox без ML.                           | Интеграционные API-тесты и браузерный E2E-путь.                           | Доказанное качество AI.                                           |
| M3 · Помощь в маршрутизации  | Версионная рекомендация, уверенность, отказ при неопределённости и исправление человеком.              | Манифест данных, тест утечки, срезы качества, калибровка.                 | Автономное назначение и выполнение fine-tuning без доказательств. |
| M4 · Похожие обращения       | Поиск кандидатов с основаниями при сохранении отдельных ID обращений.                                  | Размеченный набор пар, тест задержки и E2E проверки дублей.               | Автоматическое слияние.                                           |
| M5 · Инциденты и адаптер     | Подтверждённый состав инцидента, идемпотентная доставка, повторы и сверка.                             | Контракт адаптера, тест сбоя, запись replay.                              | Национальную живую интеграцию.                                    |
| M6 · Ситуационный центр      | Охват, свежесть, тренды, сроки, отчёты и разрешённые вопросы используют одинаковые определения метрик. | Версии метрик, сверка, сравнение экспорта с экраном.                      | Произвольный SQL или выдуманные нули по отсутствующим регионам.   |
| M7 · Подготовка выпуска      | Контроль доступа, нагрузка, восстановление, откат, наблюдаемость и runbooks проверены.                 | Подписанный отчёт о выпуске и записанный сценарий.                        | Полный production без внешних согласований.                       |

## Обязательные автоматические проверки

| Проверка                      | Минимальный охват                                                      |
| ----------------------------- | ---------------------------------------------------------------------- |
| Формат и lint                 | Изменённые Python, TypeScript, YAML, JSON и Markdown.                  |
| Типы и сборка                 | Backend-границы и production-сборка frontend.                          |
| Unit                          | Парсеры, состояния, правила, ранжирование и определения метрик.        |
| Property / fuzz               | Даты, кодировки, повреждённые данные, идемпотентность, статусы.        |
| Контракты                     | OpenAPI, каноническая схема, события и примеры адаптеров.              |
| Интеграция                    | Транзакции PostgreSQL, outbox, ссылки на вложения и отказ inference.   |
| E2E                           | Приём → решение → состояние доставки → аналитика.                      |
| Модели                        | Временной и региональный split, утечка, калибровка, языки, OOD.        |
| Безопасность                  | Идентификация, доступ по регионам, prompt injection, экспорт, секреты. |
| Нагрузка и отказоустойчивость | Критические API, очередь, поиск, backlog, потеря ML и адаптера.        |
| Восстановление                | БД, объекты, модельные алиасы и конфигурация.                          |

## Критические сценарии

1. Повторное создание с тем же idempotency key даёт одно обращение.
2. Казахское или смешанное обращение можно направить вручную при отказе ML.
3. Низкая уверенность и OOD никогда не назначают службу автоматически.
4. Неизвестная деловая дата остаётся `null` и исключается из временной оценки.
5. Неизвестное поле или статус источника попадает на проверку, а не тихо преобразуется.
6. При сбое внешней системы решение сохраняется, доставка помечена ожидающей.
7. Два обращения в одном инциденте сохраняют разные ID, истории и часы SLA.
8. Текст обращения не может заставить модель получить SQL, секреты или данные другого региона.
9. Экран, PDF и XLSX используют один ID метрики и срез данных.
10. Предыдущую утверждённую модель можно вернуть без миграции БД.
11. Потеря GPU не останавливает ручной приём, маршрутизацию, статус и аудит.
12. Пользователь одного региона не открывает другой изменением URL или API-параметра.
13. Переназначение фиксирует прежнюю и новую службу, автора, причину и время.
14. Отсутствующие или устаревшие данные помечены, а не отображаются нулём.
15. Проверка восстановления проходит **согласованные**, а не вымышленные целевые показатели.

Не заполняйте отсутствующие доказательства предположениями.
