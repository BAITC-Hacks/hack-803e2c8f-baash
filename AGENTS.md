# Инструкции репозитория Pulse 109

## Миссия

Создавайте production-пилот Pulse 109: федеративный слой ИИ-помощи для обращений граждан, интегрируемый с существующими региональными системами. Критический путь должен работать без ML и без внешней региональной системы.

## Прочитайте сначала: платформа уже существует

Репозиторий прошёл стадию каркаса. Ручной путь на PostgreSQL, аудит, outbox и worker, объединение и разделение инцидентов, privacy-проверки доступа, подписанные конфигурационные пакеты, SDK адаптеров и рабочее место оператора Next.js имеют исполняемый код и тесты. CI запускает четыре задания, включая контейнерный стек и проверку восстановления.

Не создавайте заново то, что уже есть. Прежде чем предлагать работу, прочитайте по порядку:

1. `docs/submission/FEATURE_STATUS.md`: что реализовано, что синтетическое, что заблокировано. Это источник текущего состояния.
2. `docs/README.md`: индекс документации.
3. `docs/governance/DECISIONS_AND_BLOCKERS.md`: перечисленные ниже внешние блокеры.
4. `contracts/`: OpenAPI, каноническая схема запроса и каталог событий — стабильные границы.

`docs/archive/IMPLEMENTATION_STATUS.md` и `docs/archive/` содержат исторические этапы. Они описывают путь к нынешнему репозиторию, а не его текущее состояние. Не принимайте старый этап за незавершённую работу.

## Приоритет источников

1. Текущий явный запрос пользователя.
2. Этот `AGENTS.md`.
3. Исполняемые контракты в `contracts/`.
4. `docs/submission/FEATURE_STATUS.md` и `docs/governance/DECISIONS_AND_BLOCKERS.md`.
5. Остальные `docs/` — обоснование и целевое состояние.

При конфликте источников останавливайтесь только если он меняет владение данными, совместимость API, безопасность, необратимое хранение или видимое пользователю поведение. Иначе выберите наиболее безопасное обратимое толкование, запишите его в `docs/governance/DECISION_LOG.md`, обновите затронутые контракты и продолжайте.

## Внешние блокеры: не закрывайте выдуманными ответами

Они принадлежат заказчику и организаторам, а не репозиторию. Правдоподобное выдуманное значение превращает честный пробел в ложное утверждение.

- `B01` остальные регионы и официальный манифест служб
- `B02` исходный текст обращения до решения, отсутствующий во всех восьми исторических выгрузках
- `B03` жизненный цикл полей и семантика утечки
- `B04` метки дубликатов
- `B05` история переназначений и исправлений
- `B06` официальная таксономия и значения SLA
- `B07` реальный региональный API, sandbox и credentials
- `B08` провайдер идентификации, сеть и профиль хостинга
- `B09` оборудование GPU
- `B10` приватность, правовое основание и сроки хранения

Не выдумывайте SLA, срок хранения, RPO или RTO, таксономию, региональный API client или число качества ML. Моделируйте возможность так, чтобы позже можно было задать реальное значение, и сохраняйте блокер видимым.

## Обязательные инварианты

- Pulse 109 не заменяет региональные CRM. Интеграции используют изолированные адаптеры и стабильный канонический контракт.
- Каждое обращение сохраняет собственный идентификатор, историю и SLA даже при связи с инцидентом.
- ИИ предлагает, человек подтверждает маршрутизацию, изменение приоритета, включение в дубликаты и сгенерированные ответы.
- Создание обращения, ручная маршрутизация, обновления статуса и аудит должны работать при недоступности всех ML-компонентов.
- Отсутствующее или неоднозначное бизнес-время остаётся отсутствующим или неоднозначным. Никогда не выдумывайте timestamps и не используйте порядок файлов молча.
- Сохраняйте неизменяемые ссылки на исходную нагрузку, происхождение данных, версию схемы и ошибки парсинга.
- Не обучайте и не оценивайте intake models на полях, созданных после решения оператора или результата исполнения.
- Неизвестные исходные статусы и новые колонки источника направляются на проверку mapping или в карантин. Никогда не приводите их молча.
- Исходные PII отделены от feature data. Не помещайте текст обращения, имена, адреса, телефоны или идентификаторы в логи, метки метрик или трассы.
- Запрещены автоматическое объединение дубликатов, произвольный LLM SQL, автономное рискованное назначение и неподтверждённый сгенерированный ответ.
- Первый пилот поддерживает не более двух GPU и имеет явные CPU и lexical резервные пути.
- Синтетические данные разрешены только для контрактных, UI, отказных и нагрузочных тестов. Они должны быть помечены как синтетические и исключены из заявленного качества модели.

## Архитектурные ограничения

- Сохраняйте модульное бизнес-ядро FastAPI. Не разбивайте его на множество микросервисов.
- Запускайте web, core API, worker, ML inference и каждый адаптер отдельными процессами или контейнерами.
- Используйте PostgreSQL как источник истины, PostGIS для географии и pgvector для векторного поиска.
- До добавления брокера сообщений используйте транзакционный outbox и worker с `FOR UPDATE SKIP LOCKED`.
- Используйте S3-compatible object storage для вложений и неизменяемых артефактов. Redis необязателен и никогда не является источником истины.
- Сохраняйте принадлежащие модулям схемы PostgreSQL и интерфейсы репозиториев. Запись между модулями идёт через application services.
- Стабильные границы — OpenAPI, JSON Schema и event envelopes. Внутренние Python imports не являются публичными контрактами.
- Не добавляйте Kafka, Neo4j, Elasticsearch, ClickHouse или кластер Kubernetes без измеренной потребности, записанной в `docs/governance/DECISION_LOG.md`. PostgreSQL покрывает масштаб пилота.

## Демонстрационный профиль

`PULSE109_PROFILE=demo` запускает реальные API, PostgreSQL, миграции, бизнес-сервисы, аудит, outbox и worker. Только обращения, внешние квитанции доставки и demo identities синтетические, и каждое помечено соответствующим образом.

- `uv run python scripts/demo_runtime.py up` собирает, применяет миграции, ждёт готовности и заполняет синтетический ALA demo world, включая 120 дней истории.
- `prepare` проходит API workflow, сбрасывает только demo volumes, снова заполняет и проверяет Radar, Ask Pulse, прогнозы и экспорт. Закреплённое время fixture должно быть близко к реальному времени для живого Radar.
- `reset` удаляет только volumes проекта `pulse109-demo`. `down` сохраняет их.
- `verify` запускает проверки среды и полный API-сценарий в `scripts/verify_demo_flow.py`.
- `docs/demo/DEMO_RUNBOOK.md` содержит маршрут действий в интерфейсе.

Не заставляйте demo path работать заменой на in-memory repository, выдуманной квитанцией доставки или переименованием синтетического результата в реальный.

## Метод работы

1. До редактирования изучите репозиторий, инструкции, код, контракты и git status.
2. Завершите один вертикальный срез и его тесты прежде, чем расширять объём.
3. Не перепроектируйте архитектуру только из-за моды на инструмент. Перед добавлением базы, брокера или сервиса запишите benchmark или конкретную потребность во владении.
4. Сохраняйте изменения пользователя и постороннюю работу. Не выполняйте разрушительных git operations. Другие участники пушат в эту ветку: делайте fetch прежде, чем считать дерево актуальным.
5. Поддерживайте прямую совместимость миграций. Не редактируйте применённую миграцию — создавайте новую. Выводите head из файлов миграций, не фиксируйте его в script/workflow.
6. После существенного изменения запускайте минимальные значимые проверки. До объявления завершения выполните lint, typecheck и test suite.
7. Проверьте итоговый diff на утечки, нарушения контрактов, отсутствующие пути ошибок и недокументированное поведение.
8. Проекция между двумя словарями должна быть полной. Частичная передаёт несопоставленные значения сериализатору и становится production `500`.

## Команды репозитория

Доступны через корневой `Makefile` и Windows runner `scripts/tasks.ps1`:

`bootstrap`, `format`, `lint`, `typecheck`, `test`, `contract-test`, `e2e`, `build`, `up`, `down`.

Команды должны быть неинтерактивными, завершаться ненулевым кодом при ошибке и работать из корня репозитория. PostgreSQL integration tests требуют `PULSE109_TEST_DATABASE_URL`. Без него pytest показывает skipped, что не равно прохождению. Если проверка недоступна в этой среде, запишите точную причину и следующую исполнимую проверку.

## Критерий завершения

Изменение завершено только когда поведение, тесты, контракты, миграции, конфигурация и документация согласованы. Никогда не объявляйте работу завершённой только по screenshot или зелёной сборке. Укажите выполненные команды, результаты, известные ограничения и оставшуюся работу.
